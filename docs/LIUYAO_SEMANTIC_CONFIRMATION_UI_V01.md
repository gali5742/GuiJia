# 确认优先：可操作交互原型 v0.1

日期：2026-10-12（Asia/Tokyo）。交互范围与约束先提交于 `9fd1582`。

**已将角色／目标接口做成独立页面：用户逐项确认目标及资金角色，确认清单完整，再为多件事选择一个主要目标。修改问题或清单会使原确认状态和候选检查结果失效。**

入口是 `demos/liuyao-role-target-confirmation.html`。新增会话模块组合冻结的 gate API；原接口、模型、证据提取器和生产入口不变。本轮没有再撰写自然语言评测集、训练、编码或调阈值。

## 使用流程

1. 写下原问题，点击“开始确认”。页面不自动提取角色或目标。
2. 点击一项，明确确认这件事及自己的角色并加入清单。可给目标取短名，区分同类的两笔款项，也可继续添加其他目标。
3. 点击“清单完整，确认这些目标”。此前即使每个目标已由用户确认，完整清单的来源仍是 `unverified`，两个分支都不放行。
4. 多个目标时，另选这次先看哪一件。单个目标直接成为本次主要目标。

“暂时还不能确定”停止本次确认；范围外或替第三方问款项可以选择“其他事情”退出。没有靠提取标签填充或自动选定目标，也没有预先把一个选项当成用户回答。

现阶段仍只支持问卦者本人的新借入、新出借、收债、还债、经营与资本收益六种完整选择。每个资金选项同时说明占问目标和所需角色；未知角色不会被推断为某个方向。这页不展示自动提取的猜测。

## 状态与确认来源

每个目标的 intent、role 及确认记录都由冻结接口的 `applyAnswer` 在明确选择后生成。会话模块合并这些记录，分配独立目标 ID，并在用户确认清单时记录清单确认动作。可选短名只用于显示，不能改写角色或事件类型。

同类目标保留为多个独立实例，不按路线或意图去重。两笔借款可以叫“借款甲”和“借款乙”，并分别进入主要目标选项。

对外快照不可变；选择请求绑定当前问句、版本和整个清单。修改清单后再使用旧的添加／主要目标请求，或篡改请求内容，均被拒绝。具体规则是：

| 操作 | 后果 |
| --- | --- |
| 编辑原问题 | 立即清空所有目标、回复、主要目标及候选结果；需重新开始 |
| 再点击“开始确认” | 为当前问题创建全新的会话 |
| 修改已确认清单 | 保留此前逐项确认的事实，取消清单完整性与主要目标确认，清空候选结果 |
| 移除一个目标 | 清单保持未确认，旧请求失效；空清单不能完成确认 |
| 修改模拟候选或上游条件 | 仅清空上一份候选检查结果，保留目标确认 |
| 用户仍不确定或退出范围 | 停止本次确认，不反复询问同一个问题 |

页面只在内存中保存会话；不写 localStorage、sessionStorage，不发送问句或选择。文本和短名用 `textContent` 显示；输入的标记不会被当作 HTML 执行。

## 单独的模拟候选检查

完成确认后，可展开“接口检查（模拟候选）”。它用于开发者检查约束，使用手工选择的候选、合成全部 22 路线分数、一个诊断阈值和模拟上游条件，没有调用真实分类器或编码器。

候选独立于确认事实选择，页面不会根据 `confirmedRoute` 改写候选。Arbitration 和 Fallback 都拒绝方向不一致的候选；Semantic Act、Sufficiency 和 unsupportedTargets 仍可以阻止选择。Routeability 继续只约束 Fallback，保持原 Arbitration 政策；Fallback 两头接纳不选择路线。

确认完成显示的是“本次主要目标及所需资金角色已确认”。只有模拟检查通过时才在开发面板显示选定路线；这不代表模型已自动判断正确，也不产生占断。

## 实际验证

Node.js 22.23.3 上，12 项新增会话检查与 22 项原接口检查，共 **34 项通过**。新增检查覆盖清单确认、重复意图、多目标选择、来源记录、旧请求、修改、退出及候选冲突。

真实 Chromium 151.0.7922.173 上，**15 组浏览器功能检查通过**，包含六种选择、多目标、同类两笔款项、两条分支的候选冲突、上游阻止、候选变更、编辑失效、退出、文本注入、刷新清空、键盘和 390px 手机布局。JavaScript 错误及非预期网络请求均为 0。

这些是合成交互夹具的实际点击与输入，不是真实用户研究，不测自然语言准确率或用户理解正确率。夹具中单个目标需 2 次明确动作（选择、确认清单），两个目标需 4 次（两次选择、确认清单、选择主要目标）；不含输入问句，不代表真实完成率、耗时或负担可接受性。

另实际运行常规启动命令，逐字节核验六项 HTTP 资源及首页入口，确认 HEAD 可用、未列入资源返回 404、POST 返回 405。检查记录分别保存于同前缀的 `-browser-checks.json`、`-startup-checks.json`。

初始浏览器测量使用 `isDisabled()` 查询 fieldset，不符合工具的判断方式；改为同时检查原生 fieldset.disabled 和实际提交按钮，保留真实禁用断言。额外尝试直接打开本地 HTML，被浏览器管理策略以 `ERR_BLOCKED_BY_ADMINISTRATOR` 拒绝；没有调整策略或宣称直接文件启动成功。两项诊断保存在 `-runtime-notes.json`，工作方式采用已验证的 HTTP。

## 运行

在仓库根目录：

```bash
source /workspace/.guijia-setup/activate.sh
cd /workspace/GuiJia
export NODE_OPTIONS='--require ./scripts/liuyao-semantic-v013-candidate-v07-evaluation-read-guard.cjs'
node scripts/serve-liuyao-semantic-confirmation-demo-v01.mjs
```

启动命令在当前终端持续运行，默认仅监听本机 8787 端口。首页 `/` 或 `/demos/liuyao-role-target-confirmation.html` 是同一个入口。需要其他空闲端口时设置 `GUIJIA_CONFIRMATION_PORT`；不要停止不相关进程。Ctrl-C 可停止自己启动的服务。

服务器只加载并提供 HTML、CSS、页面逻辑、会话模块和冻结 gate／inventory 六项资源，没有目录服务或评测数据访问。原型不在生产构建的 HTML 入口清单中，不需要刷新 `.site`，也没有发布到 GitHub Pages。

定向验证命令：

```bash
node --test tests/liuyao-semantic-confirmation-session-v01-tests.mjs tests/liuyao-semantic-role-target-gate-v01-tests.mjs
node --import /workspace/.guijia-setup/browser-runtime.mjs scripts/check-liuyao-semantic-confirmation-ui-v01.mjs
```

浏览器检查使用已安装的仓库外 Playwright 和系统 Chromium，自己启动并关闭临时演示服务器；不依赖常驻 8787 服务。无需新增包、网络域名或密钥。在其他机器使用其已有 Playwright 及可用 Chromium，必要时指定 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`。

## 当前边界与后续取舍

确认接口可实际操作，但仍依赖用户理解选项、正确列全目标与选择主要目标；没有证明这些条件在真实用户中成立。跨句指代、第三方主体和自动事实提取仍未实现。

下一步应先收集少量真实操作反馈，检查“是否选对角色、是否漏列目标、确认是否难懂或繁琐”。在这些问题明确前，保留当前独立入口，不扩大提取器修补或恢复大规模模型优化。

本轮无新云 CI，无正式组件通过、生产集成或 Phase C 许可。独立／盲评／预留研究读取为 NO；既有失败及读取事件保留。
